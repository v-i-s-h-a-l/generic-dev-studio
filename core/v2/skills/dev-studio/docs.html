Quick Start

Smallest set of commands and current traffic state.

Put the role after /dev-studio. If no role token is present, the invocation opens the lightweight manager landing for conversational shaping and status. A role with no request, such as /dev-studio reviewer, opens that role's landing instead of running a heavy default action.

/dev-studio manager /dev-studio reviewer /dev-studio release-manager /dev-studio manager resume-plan /dev-studio worker <contract> /dev-studio checkpoint /dev-studio worker checkpoint /dev-studio worker resume-checkpoint /dev-studio reviewer review /dev-studio perf profile /dev-studio release-manager

Usage Workflows

What to type for common single-task, multi-task, hotfix, and release-followup loops.

Single Task

Use the manager when the work still needs shaping. Expect a scoped plan, one worker contract, local checks, review, and a short summary.

/dev-studio manager fix the settings crash

Direct Worker Contract

Use a worker directly only when the contract is already bounded and the files or acceptance criteria are clear.

/dev-studio worker T123

Review Before Merge

Use the reviewer when you have a diff, PR, or phase outcome and want compliance, safety, and missed-test checks.

/dev-studio reviewer review

Parallel Independent Tasks

Ask the manager to split independent work. Expect separate worktrees, separate PRs or summaries, and no shared-index edits.

/dev-studio manager split these three unrelated bugs into parallel worker contracts

Parallel Chains

Use chain manifests when the repo already has an issue chain. Dry-run first, then launch one independent chain per shell session.

scripts/studio-chain-runner.sh <manifest> --only <chain> --dry-run scripts/studio-chain-runner.sh <manifest> --only <chain>

Hotfix Bug

Tell the manager it is a hotfix and name the risk. Expect the smallest patch, the fastest relevant checks, review, and release-manager escalation if a build or public message is needed.

/dev-studio manager hotfix: fix the launch crash from the latest TestFlight build

General Bug After TestFlight

Use this when the issue is real but not an emergency. Expect triage, reproduction notes, one or more worker contracts, QA or flow-test evidence if the surface is user-facing, then release readiness if needed.

/dev-studio manager bug: the new TestFlight feature loses state after relaunch

Performance Investigation

Use perf when the problem is memory, CPU, thermal, battery, network, or instrumentation evidence rather than ordinary correctness.

/dev-studio perf profile the new editor flow

Release Readiness

Use release-manager after implementation evidence exists. It can assemble blockers and notes; tagging, publishing, TestFlight, and App Store actions still need operator approval.

/dev-studio release-manager prepare beta readiness for the latest merged fixes

Checkpoint Resume

Use bare checkpoint only for manager-shaped routing. Put the role before checkpoint when the role already owns the state; checkpoint artifacts do not replace summaries, verdicts, packets, checklists, or event logs.

/dev-studio checkpoint /dev-studio worker checkpoint /dev-studio reviewer resume-checkpoint

Host Availability

Where `/dev-studio` comes from in Claude and how Codex loads the router skill.

Claude Code

The visible slash command is globally installed at ~/.claude/commands/dev-studio.md. Claude Code does not install the router as a global skill, so the picker has one canonical /dev-studio row.

/dev-studio manager resume-plan /dev-studio reviewer review

Codex

The router skill is globally linked at ~/.codex/skills/dev-studio. Codex hosts may not expose skills in the $ picker; invoke it by naming the skill and role in the request.

Use dev-studio manager to resume the plan. Use dev-studio perf to profile the urgent task.

Sync

After pulling changes, run install or host sync from this repo. It refreshes global command and skill links and removes stale deleted v1 skill links.

scripts/install.sh scripts/sync-host-skills.sh --all

Scope

The v2 router is globally discoverable but project-aware. The current working project supplies task context; the studio repo supplies role contracts and orchestration scripts.

commands/dev-studio.md core/v2/skills/dev-studio/ ~/.codex/skills/dev-studio

Existing State

What happens to old task IDs, Chanakya master-plan data, and runtime artifacts.

The v2 router changes the command surface, not the project ledger. Existing task IDs, briefs, debriefs, reviews, event logs, chain runs, worktrees, and rendered master plans stay under ~/.dev-studio/<project>/.

The master plan is a rendered projection. Structured task state lives under plans/tasks/*.yaml; legacy markdown surfaces are import or archive inputs where migration already moved them.

Expected continuity

A pre-v2 task ID remains the same task reference. The manager should read the existing runtime state before minting or dispatching new work.

Ingest Routing

Ingest follows the current git repository by default. Cross-context Forge/Studio capture is explicit and resolved by scripts/dev-studio-ingest-resolve.sh.

scripts/dev-studio-ingest-resolve.sh --cwd "$PWD" scripts/dev-studio-ingest-resolve.sh --cwd "$PWD" --scope studio

Automation

Which parts are automated today and which still need an explicit user/session trigger.

Automated Today

Worker queues, isolated task worktrees, chain-runner resume state, PR headless review, phase review wrappers, event logs, and generated master-plan views are implemented as scripts and runtime artifacts.

User-Started

The studio does not run as an always-on autonomous daemon by default. A human starts a manager session, worker panes, chain runner, release flow, or scheduled helper.

Chain Runs

Issue chains can run with persisted private reports and resume markers. Use dry-run first, then launch independent chains in separate shells when their write boundaries are disjoint.

scripts/studio-chain-runner.sh <manifest> --dry-run scripts/studio-chain-runner.sh <manifest> --auto

Fleet Work

Multiple workers can watch a queue and claim tasks atomically. The manager dispatches; workers take isolated worktrees and report completion evidence.

/dev-studio worker scripts/worker-status.sh

Canonical Roles

Which roles are open for direct use, contracted but manager-mediated, or registry-only.

What reserved means

Reserved does not mean the name is forgotten. It means the router recognizes and protects that role or alias, but routine direct-user workflows are not the default surface yet. Some reserved roles have active contracts and are normally reached through manager-shaped work; registry-only roles are authority or adapter concepts rather than runnable task agents.

manager

Owns intake, prioritization, lifecycle state, dispatch, status, user escalation, and final acceptance routing.

direct usealiases: chanakya, coordinator, orchestrator

worker

Implements one bounded task contract in an isolated worktree.

direct usealiases: achilles, implementer

reviewer

Verifies plan or spec compliance, code quality, safety gates, and contract adherence.

direct usealiases: argus, verifier

perf

Investigates performance, battery, memory, thermal, and instrumentation evidence.

direct usealiases: apollo, performance, performance-engineer

planner

Active contract for executable plans, dependency graphs, acceptance criteria, and worker contracts.

contracted, manager-mediatedaliases: architect, luban, lu-ban

qa-engineer

Active contract for automated test strategy and stable QA targets beyond the worker's local checks.

contracted, manager-mediatedaliases: qa, chiron, synthetic-qa

flow-tester

Active contract for exploratory user-flow checklists tied to builds, branches, and evidence.

contracted, manager-mediatedaliases: flow, manual-qa, exploratory-tester

release-manager

Active contract for release packets, blocker state, notes, tags, TestFlight, and App Store readiness.

contracted, approval-gatedaliases: release, shipper

host-adapter

Registry role for host capability and adapter operations. It is not a general task agent.

registry-only reservedaliases: adapter, host

operator

Human authority for irreversible, ambiguous, or externally visible decisions.

non-routablealiases: user, human, owner

Resolution Order

How canonical names, aliases, old names, and missing role tokens resolve.
  1. Explicit canonical role routes directly, such as /dev-studio worker <contract>.
  2. Compatibility alias resolves through scripts/v2-role-resolve.sh, such as /dev-studio achilles <contract>.
  3. Former top-level names remain aliases only when placed under /dev-studio.
  4. A bare role token opens that role's lightweight landing.
  5. No role token opens the manager landing.
  6. Unknown role tokens fail before side effects.

Landings stay lightweight

Bare-role landings load role contracts and cheap cwd/profile context only. They suggest next moves, then report the direct command after the user locks in a workflow.

Router Boundaries

What the umbrella command owns and what downstream roles own.

The umbrella router chooses a role contract. Mode procedure, authority checks, handoff validation, event emission, and project-profile commands are owned by the selected role or downstream primitive.

Checkpoint and resume-checkpoint are lifecycle actions. Bare invocations land in manager for shaping; explicit role invocations keep checkpoint content owned by that role and follow the compact shared checkpoint contract.

This page is the studio-layer command surface. It intentionally does not duplicate deleted v1 agent manuals or task-layer command tables.
