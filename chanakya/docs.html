Quick Reference

Triggered by /chanakya studio-feedback or "capture this as feedback".

Achilles — The Warrior

/achilles T001 Pick up a briefed task (implementation or test) in an isolated worktree, self-review, gate on green build, merge locally
/achilles T001 --wait Same pipeline, but pauses up to 10 min for your test feedback before merging
/achilles T001 --force-build Force a full xcodebuild even for XS/S tasks (escape hatch)
/achilles T001 --ignore-build-debt Override the build-debt block. Recorded in the debrief; use sparingly
/achilles T001 --dry-run Simulate every write and event; reads + LSP run normally. Exit 0 = would succeed, exit 2 = surfaced a problem. Phase 2.5 pilot — other modes adopt the pattern in 2.6
/achilles Direct mode — free-form task, no brief required
/achilles build On-demand build check at HEAD. Green resets debt; red auto-bisects and files a P0 fix
/achilles debrief Direct-debrief: capture an in-chat bug-fix or quick-change into a YAML debrief — scans transcript + git diff HEAD, asks inline about tests, writes to plans/debriefs/. No brief, no worktree, no Argus, no git action.
/achilles push-tf Wraps /pushTFBuild — archives, uploads to TestFlight, then debriefs Chanakya with task-to-build mapping
/achilles app-store Wraps /fullSendToAppStore — submits to App Store, then debriefs Chanakya with release tracking data
/achilles studio-feedback Same contract as /chanakya studio-feedback. In one-shot subagent runs, write the feedback file directly to the canonical inbox — no paste, no debrief-block duplication.

Argus — The Watcher

/argus Review the current worktree (auto-invoked by Achilles pre-merge). Checks cross-file regression risk, edge cases, test adequacy, diff anomalies, staleness, secrets.
/argus T001 Review a specific task's worktree standalone, outside the Achilles flow
Week 1 posture: only hard checks block (compile/test failure, secrets, staleness). Everything else flags — merge proceeds and Chanakya auto-files follow-up tasks from flagged findings. Promote checks to blocks after observing real signal.
Scope caps (token budget guardrails): cross-file scan capped at 10 neighbor files × 50 lines each; diffs over 500 lines load only the 500 most-changed lines; XS single-file diffs under 20 lines skip Argus entirely. Every triggered cap emits a review_scoped event (cap type + actual vs limit) so you can tune thresholds from longitudinal data.
Default is merge-immediately. Achilles invokes Argus pre-merge (Step 8.5), then merges on approved/flagged. Chanakya processes findings from the event log on its next sweep. Batch-test with /chanakya test-manifest or /chanakya test-flow when ready.

Model Recommendations

Per-agent model defaults — tune for cost/quality without losing capability where it matters.

AgentDefaultWhen to upgrade / downgrade
Chanakya Sonnet Orchestration is structured reads/writes — Sonnet handles it. Use Opus for ambiguous PRD intake; use Haiku for event-processing modes (compact, auto-sweep ticks, sync-slack) for ~15× cost reduction.
Achilles Opus (always) Code generation never downgrades. The worker parent bash-loop (scripts/achilles-worker.sh) can run on Haiku since it only dispatches; child claude -p subprocesses stay on Opus.
Argus Opus (always) Reasoning-heavy edge-case analysis requires the strongest model. Do not downgrade.

Composite Commands

Multi-step sequences that chain existing modes. One command, minimal manual involvement.

Chanakya Composites

/chanakya brief-all Brief every pending task in priority order. Skips implementation briefs if debt is blocked.
/chanakya ship T001,T002 Brief + generate phased dispatch plan for Achilles. ship next, ship next 3, ship all also work.
/chanakya sweep-debt Identify all pending test sub-tasks and build checks. Brief them, generate dispatch plan to get back to green.
/chanakya verify Guided flow: generate test-flow → you test → promote → review-feedback → verified. All in one session.
/chanakya compact Archive verified tasks, regenerate Dashboard + Module Index, trim master plan to actionable items only. Also sweeps artifacts (event logs, orphaned xcresult bundles, stale markers, gitignored Playwright MCP telemetry via git clean -fdX). --dry-run previews. --no-sweep-artifacts skips artifact cleanup. --auto-compact prints cron setup for nightly 03:00 runs.

Achilles Composites

/achilles group T015 Execute implementation + unit tests + UI tests sequentially in one session. Stops on first failure.
/achilles next Pick the highest-priority ready task and execute it. next 3 generates a dispatch plan for parallel tabs.
/achilles test-suite unit Run the full unit test suite at HEAD. Green resets unit test debt. Also: ui, all.
The hands-off workflow: /chanakya ship all → run the printed commands in parallel tabs → /chanakya verify when done. Three user actions for a full feature cycle.

Multi-Worker Fleet BETA

File-based IPC that lets one Chanakya session fan tasks out to N independent Achilles worker panes. Each worker spawns a fresh claude -p "/achilles <id>" per task — clean context every time, no harness changes.

One-time setup

brew install fswatch coreutils
chmod +x scripts/*.sh

Daily flow

Recommended: launch Claude in N panes with claude --dangerously-skip-permissions, turn on iTerm Broadcast Input (Cmd+Opt+I), and type /achilles worker once. Every Claude session runs the worker mode, each pane atomically claims the lowest free slot (1, 2, 3, …) via a worker-N/.lock dir, and the parent Claude session stays available for status / shutdown questions. Tasks themselves still spawn in fresh claude -p subprocesses — per-task context stays clean.

Alternative (no Claude wrapper): run the bash worker directly — scripts/achilles-worker.sh in each pane. Same atomic claim, no Claude session around it.

Then dispatch from your Chanakya session or any shell.

/achilles worker [N] Inside a Claude session. Atomically claims a slot, starts the bash watch loop in the background (with ACHILLES_UNATTENDED=1 so child claude -p subprocesses inherit your dangerous-skip-permissions intent), and stays available to answer status / stop questions. Use this from broadcast-typed panes.
scripts/achilles-worker.sh [N] Pure bash, no Claude wrapper. Same atomic claim and watch loop. Use this if you don't want a Claude session around it. ACHILLES_UNATTENDED=1 enables --dangerously-skip-permissions for child subprocesses.
scripts/achilles-dispatch.sh <task-id> [worker-N|any] Writes a task file to a worker inbox. Default any picks the alive worker with the lowest busy + pending load. Pass extra flags after -- (e.g. -- --wait --force-build). For batch dispatch prefer the work-stealing queue.
scripts/achilles-queue.sh {enqueue|drain|list|depth|clear} Work-stealing dispatch queue. enqueue <id> appends; drain hands head-of-queue tasks to each free worker (busy=0 AND pending=0). Chanakya calls drain on every task_completed event so fast workers don't sit idle behind slow ones.
scripts/worker-status.sh One-shot table of every worker: state (idle/busy), pending / done / rescue counts, heartbeat age, current task id.
scripts/achilles-cancel.sh <task-id> Removes pending dispatches matching the id. Cannot stop in-flight tasks — kill the worker pane for that. Does not touch the dispatch queue; use achilles-queue.sh clear for that.

Chanakya sub-commands

Sub-commandBehavior
--worker-statusSurface the fleet table. Use before any dispatch to confirm capacity.
--dispatch <task-id> [worker-N|any]Shell out to achilles-dispatch.sh. Refuses if task status is not briefed.
--dispatch-many <ids…>Legacy upfront fan-out — one --dispatch any per id. Superseded by --queue-enqueue + --queue-drain for anything more than 1–2 tasks.
--queue-enqueue <task-id>Append to the per-project work-stealing queue. No-op if already queued.
--queue-drainHand head-of-queue tasks to each free worker (busy=0 AND pending=0). Called automatically by Chanakya on task_completed.
--queue-list / --queue-depth / --queue-clearInspect or reset the queue.
--cancel <task-id>Remove pending dispatches across all inboxes. Does not touch the queue.

~/.dev-studio/<project>/.runtime/achilles-inbox/worker-<N>/

  busy                     # present iff a task is in-flight (contents = task-id)
  inbox/<ts>-<id>.task     # pending dispatches (fswatch target)
  done/<ts>-<id>.task      # completed
  rescue/<ts>-<id>.task    # timed-out / malformed; operator decides retry

Refusal rules: Chanakya refuses to dispatch when (a) the task is not briefed, (b) Build Debt is in block state and the task is not a debt-reduction task, (c) no alive workers exist and the user did not pin a specific worker, or (d) the brief contains an unresolved interactive-input gate (Phase 0 marker like "confirm with", "check Figma", "debug print" — a worker cannot answer, and the silent-stuck detector would catch it at exit).
Events stay on the existing log. worker.log is operator-facing only. Achilles inside the worker still emits task_started, task_completed, review_blocked, etc. Chanakya consumes them in Step 0E exactly as today — the worker layer is invisible to the event pipeline.

Review-waive lifecycle

Pause a review gate (e.g. Argus) during a broad refactor, with a sunset trigger and an auto-incrementing "merges skipped" counter. State lives per-project at ~/.dev-studio/<project>/state/waives/<gate>.yaml.

scripts/waive-start.sh argus "broad refactor in flight" "rebase of main complete"
scripts/waive-lift.sh argus    # reports N tasks merged without review during the pause

While a waive is active, every review_pending emission from sweep-ingest.sh bumps accumulated_count atomically. The SessionStart hook surfaces a one-line banner on every new session so a pause can't become invisible. Closes #83.

↓
/chanakya — organizes into task groups (impl + unit + integration + UI tests)
↓
/chanakya brief — writes implementation brief (with testability requirements) + test briefs
↓
/achilles T001 — implement with SOLID, accessibility IDs, localization, test seams
↓
self-review (+ testability check) → green-build gate
↓

↓ approved / flagged
merge — emit brief_completed event → debrief
↓

↓

↓
/chanakya test-flow → manual walkthrough → /chanakya review-feedback → verified

A feature isn't done when the code compiles — it's done when the task group (implementation + tests) is complete and the user has verified via manual testing.

Implementation briefs include quality mandates

Every implementation brief has a Testability Requirements section covering:

  • SOLID principles: single responsibility, protocol-based DI, focused interfaces
  • Accessibility identifiers: shared enum per module (enum AccessibilityID { enum Screen { static let element = "..." } }). Strong types, not raw strings.
  • Localization: all user-visible strings via "keyName".localized (camelCase + feature prefix). New keys added to all three .lproj files (en, hi, uk). Format strings use {placeholder} tokens. No hardcoded literals in views.
  • Test seams: protocol-based interfaces for external dependencies. Injected via initializer.
  • What NOT to do: Don't over-abstract. Pure functions are already testable. No protocol wrappers for simple value types.
Achilles enforces all mandates. During self-review, Achilles checks: are all accessibility IDs defined? Are test seams exposed? Any new singletons in business logic? Any hardcoded string literals missing .localized? Are new keys present in all three .lproj files? Any failure is a merge blocker.

Testing Architecture

Achilles handles four types of test tasks, each with type-specific execution logic:

Unit Tests (test-unit)

  • Reads parent implementation first (parent must be done)
  • Scans existing tests for reusable helpers and mocks
  • Tests business logic, view models, model transformations in isolation
  • Extracts shared helpers when patterns repeat 3+ times
  • Files refactor tasks for test utilities if they outgrow the current file

Integration Tests (test-integration)

  • Tests real module boundaries — no mocking the integration itself
  • Mocks only external services (network, disk, sensors)
  • Kept separate from unit tests (different file/group)
  • Longer running — marked with test categories where supported

UI Tests (test-ui)

  • Validates accessibility identifiers exist before writing tests
  • Uses page object pattern for screen abstractions
  • Happy path flows first, then edge cases, then error recovery
  • Bug fix tasks add regression tests reproducing the original bug
  • Removes redundant tests when new ones provide better coverage

TDD Tests (test-tdd)

  • Defines expected interfaces (protocols, method signatures)
  • Writes failing tests against those interfaces
  • Implementation task (blocked by this) makes the tests pass
  • Debrief lists exact interfaces the implementation must satisfy
Test tasks never modify production code. If production code needs changes to be testable, Achilles files a follow-up task. This keeps test PRs clean and reviewable.

Safety Guarantees

01
Uncommitted changes never touched
Achilles branches from committed HEAD into an isolated worktree. Your main checkout stays clean.
02
Red builds never merge
Step 6 gates on xcodebuild success. On failure the branch and per-task DerivedData are retained for inspection.
03
Merge conflicts never force-resolved
Achilles stops and surfaces them. Branch + DerivedData stay alive so you can resolve manually.
04
Parallel-safe: builds serialized
Per-project mkdir lock prevents SPM-cache and module-cache races across 6–10 parallel Achilles instances.
05
Parallel-safe: merges serialized
A second lock handles .git/index.lock contention, checkout races, and branch tip movement.
06
All tests pass before merge
For test tasks, all tests must be green. For implementation tasks, existing tests must not regress.
07
--wait never hangs
A ScheduleWakeup(600s) fires even if you're idle. Achilles stamps "no reply" and auto-merges.
08
Achilles never self-picks
Control returns to the user (or Chanakya) after every completion. No runaway fleets.
09
Argus blocks what must not ship
Secrets, base staleness, and compile/test failures are hard blocks regardless of week-1 posture. Argus re-runs after each fix attempt (max 3 cycles).
10
Test slots prevent simulator thrash
Argus uses a 3-slot file semaphore for concurrent test runs. XS/S reviews skip tests entirely — fast path, seconds not minutes.
11
Failure artifacts retained 48h
On any block or fail event, xcresult bundles, review files, and DerivedData survive for 48 hours. Chanakya compact only eagerly sweeps success paths.

Debt Tracking — Three Gauges

Chanakya tracks three independent debt counters. Each has warn and block thresholds. All are updated automatically on every inbox sweep.

Build Debt

Tasks merged without xcodebuild

0warn@6block@12
Unit Test Debt

Impl tasks without unit tests done

0warn@4block@8
UI Test Debt

Impl tasks without UI tests done

0warn@3block@6

Build Debt

XS/S tasks skip xcodebuild (LSP-only) to keep the fleet fast. Chanakya counts every skipped build.

CounterStateBehavior
0 – 5silentNormal operation
6 – 11warnBanner + auto-file TBUILD-<n> at the 5→6 transition
≥ 12blockRefuse new implementation briefs until resolved

Reset: /achilles build — green resets counter to 0; red auto-bisects and files a P0 fix.

Escalation triggers (force full-green regardless of size): any import, public/open, protocol, actor/async, generics, Package.swift, or new/deleted files.

Unit Test Debt

Increments when an implementation task merges but its unit test sub-task is still pending/briefed.

CounterStateBehavior
0 – 3silentNormal operation
4 – 7warnBanner + auto-file TUNIT-<n> (run full unit test suite)
≥ 8blockRefuse new implementation briefs. Test briefs always allowed.

Decrement: When a unit test sub-task's debrief is processed, counter decrements and the parent is removed from Untested since.

UI Test Debt

Same logic, tighter thresholds — UI tests are more expensive to catch up on.

CounterStateBehavior
0 – 2silentNormal operation
3 – 5warnBanner + auto-file TUI-<n> (run full UI test suite)
≥ 6blockRefuse new implementation briefs. Test briefs always allowed.

Key rule: All three debt systems are independent. Resolving one doesn't unblock the others. Test briefs are never blocked — they're the solution.

Master plan header tracks all three. The ## Build Debt and ## Test Debt blocks at the top of chanakya-master.md are the source of truth. Never hand-edit — Chanakya's Step 0 owns them.

A human-readable companion to test-manifest, organized by user journey rather than by task. Produces numbered round files that are never overwritten.

Key features

  • Partial continuation: detects half-finished rounds and asks whether to continue or start fresh
  • Retest tracking: [R<prev> retest] tags for failed cases from prior rounds
  • Severity tags: [critical] / [important] auto-derived from task priority
  • Performance checkpoints: inline [perf] cases with Timing:___ and Perf baseline: fields

  • Cross-round diff: --diff N shows regressions, fixes, and perf deltas with 20% thresholds
  • Task crosswalk: bidirectional table mapping tasks ↔ sections

Journey map (optional)

Drop a journey-map.md file in ~/.dev-studio/<project>/ to define your preferred section ordering. Without it, Chanakya auto-infers sections from file paths, skill tags, and brief titles.

Release Tracking

Achilles wraps your existing build skills (/pushTFBuild, /fullSendToAppStore) without modifying them. It adds a debrief layer that maps builds to tasks.

How it works

  1. Pre-flight: Achilles reads the master plan, collects all tasks merged since the last release of that type
  2. Build: Your existing skill runs exactly as-is — you interact with it normally
  3. Debrief: Achilles writes a release debrief to Chanakya's inbox with the build number, version, and task list
  4. Tracking: Chanakya processes the debrief, adds a row to the Release Log, and tags each task with Released in: TF-3031

What this enables

01
Which tasks shipped in build 3031?
Read the ## Release Log table in the master plan. Each row lists the tasks included.
02
Which build broke feature X?
Check the Released in: field on the task. Compare with the build where the regression appeared.
03
Time for a new TestFlight?
/chanakya status shows tasks merged since the last TestFlight and suggests /achilles push-tf when the count is > 0.
04
Release notes from task history
The Release Log + task titles give you a structured changelist for any build, independent of commit messages.

    chanakya-master.md # Active tasks only (Dashboard + debt + pending/done)

~/.dev-studio/<project>/

Why outside ~/.claude/? Keeps both agents clear of Claude Code's self-mod permission guard, so they can read/write artifacts unattended.

Tips

01
Start small
Try /achilles on a bug fix first. Then /chanakya on a small feature. Scale up as you get comfortable.
02
Task groups scale with complexity
A trivial fix gets impl only. A feature gets impl + unit + UI tests. Chanakya decides — you approve.
03
Test sub-tasks run in parallel
After T015 merges, fire /achilles T015a and /achilles T015c in separate tabs. They're independent.
04
Don't over-abstract for testability
Pure functions are already testable. Achilles only adds protocols where the brief's Test Seams section explicitly calls for them.
05
Accessibility IDs are committed early
The enum file is a separate, early commit in the implementation task. UI test tasks depend on it.
06
Use --smoke for quick checks
/chanakya test-flow --smoke generates a minimal walkthrough — one critical case per section + all retests. 10 minutes vs 45.
07
--diff tracks quality over time
/chanakya test-flow --diff 2 compares rounds. Flags regressions, confirms fixes, shows perf deltas with 20% thresholds.
08
--promote bridges manual to automated
After a passing round, --promote generates a pre-checked user-testing.md. Run review-feedback to mark tasks verified.
09
Debt gauges keep you honest
Three independent counters (build, unit test, UI test). Each warns early and blocks late. Test briefs are never blocked — they're the solution.
10
Red builds don't merge
If Step 6 fails, Achilles stops and retains the branch + DerivedData. Inspect under ~/.dev-studio/<project>/worktrees/<id>/.
11
Journey map is optional
Drop a journey-map.md in your project root to define section ordering for test-flow. Without it, sections are auto-inferred.
12
Briefs are snapshots
If the codebase changes between briefing and execution, regenerate with /chanakya brief T001.
13
Compact when the plan bloats
/chanakya compact --dry-run shows what would move. Run without the flag to archive verified tasks and slim the plan to ~500 lines. Full history is preserved in chanakya-archive.md.
