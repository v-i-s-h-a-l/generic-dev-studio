Onboarding a machine

One unified wizard — scripts/bootstrap.sh — for any role: manager (primary, runs agents), worker (headless worker), or dual (rare; both).

Host-agnostic. Agents-only is just "manager with no workers registered" — same wizard, fewer steps.

Quick start

Onboard any Mac as a manager (your primary dev box, runs the agents), worker (a headless build box), or dual. Same wizard for all three.

git clone https://github.com/v-i-s-h-a-l/generic-dev-studio.git
cd generic-dev-studio
./scripts/bootstrap.sh --role manager   # zero prompts
./scripts/bootstrap.sh                  # auto-pilot, prompts for role only

The wizard runs as plain bash — no AI required at install time. Auto-pilot is the default: every step takes its smart default based on your machine state, and the only mandatory input is role (skipped if you pass --role). Pass --interactive to be prompted at every step. Tweak anything later with scripts/configure.sh.

From inside Claude Code

If you already have a Claude Code session open in the cloned repo, the slash command wraps the same wizard:

/studio-setup                    # auto-pilot — prompts for role only
/studio-setup --manager          # zero-prompt manager onboarding
/studio-setup --worker           # zero-prompt worker (id = hostname)
/studio-setup --worker --id mini --roles swift-test,xcodebuild
/studio-setup --dual             # both roles on one box
/studio-setup --interactive      # prompt at every step (legacy)
/studio-setup --dry-run          # preview without changing anything
/studio-setup --help             # this guide + usage summary

The slash command runs on the current machine — it does not SSH anywhere. To onboard a different machine, SSH there first and run it from a session on that box.

Install

Zero-prompt install (defaults)

Sensible defaults for every step; no questions asked. Use this when you just want it working — you can configure anything afterwards. This is the default behavior when a --role is supplied.

./scripts/bootstrap.sh --role manager
./scripts/bootstrap.sh --role worker --id mini --worker-roles swift-test,xcodebuild
./scripts/bootstrap.sh --role dual

Auto-pilot (no role flag)

Same as zero-prompt, except the wizard prompts once for the role. Otherwise it derives every decision from machine state.

./scripts/bootstrap.sh

Interactive install (legacy)

Walks you through every step, lets you choose. Defaults stay sensible — most prompts you can just press Enter on.

./scripts/bootstrap.sh --interactive

Preview without changing anything

./scripts/bootstrap.sh --dry-run --role manager

Configure

Post-install changes go through scripts/configure.sh. Single entry point, idempotent.

scripts/configure.sh                 # interactive menu (status + options)
scripts/configure.sh status          # one-screen state dump

scripts/configure.sh worker add      # interactively add a worker to nodes.json
scripts/configure.sh worker remove <id>
scripts/configure.sh worker enable <id>     # nodes.json: enabled = true
scripts/configure.sh worker disable <id>    # pause without de-registering
scripts/configure.sh worker scopes <id> asc,slack  # set credential scopes (#284)

scripts/configure.sh manifest        # edit worker-manifest.yaml in $EDITOR

scripts/configure.sh schedule on     # install scheduled worker-sync (launchd, nightly)
scripts/configure.sh schedule off    # remove it
scripts/configure.sh schedule run    # one-shot sync now

Wizard reference

What the 11 wizard steps actually do. Most are auto; a few need a click or a sudo password.

  1. Preflight + role + identity auto
    macOS check, architecture detect (Apple Silicon / Intel), repo-location detect, machine-id capture, role selection (skippable via --role).
  2. Homebrew + packages auto
    Installs brew + role-specific deps. For every tool already present: keep / upgrade / reinstall / skip. Non-interactive mode keeps all by default.
  3. Studio repo + agent skills auto manager · dual
    Runs install.sh to symlink agents + slash commands into ~/.claude/. Idempotent. Optional contributor git hooks.
  4. SSH identity mixed
    manager: detects existing keypair, offers ed25519 generation. worker: enables Remote Login, accepts one or more manager pubkeys pasted in.
  5. Tailscale mixed
    Detects + offers to install via brew; you do the browser sign-in. Manager gets an optional recommended ACL scaffold for the Tailnet admin console.
  6. pmset keep-awake auto worker · dual
    Applies no-sleep settings. Asks if it's an always-on box and points at the extra flags if so.
  7. Git config + Xcode mixed
    Confirms git user.name/email (manager). Detects Xcode / CLT, flags missing Xcode.app when role xcodebuild is picked.
  8. Registration auto
    worker: emits the exact nodes.json entry (with machine_id) to paste on your manager. manager: creates nodes.json skeleton if missing.
  9. Worker manifest + scheduled sync auto manager · dual, opt-in
    If at least one worker is registered, offers to create a default worker-manifest.yaml and install a nightly launchd agent that keeps workers in lock-step automatically. Both opt-in; flip later via configure.sh schedule on.
  10. Self-test + summary auto
    Role-specific health checks + pass/fail count + next-step hint. Every run logged under ~/.dev-studio/.runtime/logs/bootstrap-<ts>.log.
No fallback footgun. If you skip the wizard entirely, node-pick returns local and every dispatch runs on the manager — identical to pre-onboarding behaviour. Onboarding is purely additive.

Why + how it works

The studio's build-gate scripts (swift-test-gate.sh, task-build-gate.sh) call scripts/node-pick.sh <role> before running. If a healthy remote node with the matching role is registered, the compile + test cost lands there over SSH; otherwise it runs locally. The laptop keeps Xcode / simulators responsive; the node handles the heat.

The moving parts

Tailscale vs local SSH

Use Tailscale. Free (personal tier: 100 devices, 3 users). Works across networks, through NAT, with stable MagicDNS hostnames. Local .local (Bonjour) is flaky across some wifi / VPN setups and hostnames can shift. The small extra install cost pays back the first time you try to build from a cafe.

Roles

A node advertises which kinds of work it can absorb via a roles array in nodes.json. The gate that wants the work asks for its role:

RoleRequested byNode needs
swift-testswift-test-gate.shSwift toolchain (comes with Xcode CLT)
xcodebuildtask-build-gate.sh full-greenFull Xcode + matching simulators
snapshot-canonicalsnapshot-sync.shFixed Xcode/sim — reference-image generator

A node can hold any subset. Mini with full Xcode typically holds all three. A Linux worker would only hold swift-test.

Prerequisites

Two machines, two different setups. The laptop is the primary — it runs Claude Code sessions, hosts the agent skills, clones the studio repo, and dispatches commands. The node is a worker — it receives commands over SSH and runs compile/test workloads. Don't install the laptop stack on the node; don't expect the node to do agent work.

On the laptop (one-time, before onboarding any node)

This is your primary dev machine — where you run /chanakya, /achilles, /argus, where your iOS project lives, where Xcode is your editor. Setup checklist:

  • Claude Code CLI installed and signed in. The agent layer runs inside a Claude Code session on this machine.
  • This repo cloned: git clone git@github.com:v-i-s-h-a-l/generic-dev-studio.git
  • Agent skills installed globally: 
    cd generic-dev-studio
./scripts/install.sh
./scripts/verify-install.sh
    Symlinks chanakya, achilles, argus + _shared + scripts into ~/.claude/skills/ so they reach you from inside your iOS project. /studio is deliberately not installed globally — it auto-loads only when cwd is inside this repo.
  • Homebrew + studio deps (required for fleet / multi-worker mode, recommended for everyone): 
    brew install fswatch coreutils yq jq rsync
  • Tailscale — installed, signed into your tailnet. (Optional for same-LAN-only setups; strongly recommended otherwise.)
  • SSH keypair. If missing: 
    ssh-keygen -t ed25519 -C "vishalsingh" -f ~/.ssh/id_ed25519
    The node will accept this key during onboarding.
  • Xcode.app — needed for local fallback (when no node is registered or all are unreachable) and as the Xcode-version baseline every node should match.
  • Your iOS project's source repo cloned, working tree on your preferred branch.

If you're coming to the studio fresh, see README.md for the full install walkthrough including git hooks (for contributors) and fleet-prerequisite options.

On the node (the Mac you're onboarding)

A worker node is an extension of your laptop, not a second dev machine. It does not need Claude Code, doesn't host agent skills, doesn't run your shell profile. The bootstrap wizard handles the software install; this section lists what the physical machine needs before you can run the wizard.

  • macOS, admin account you can log into physically or via screen sharing for the first 5 minutes (to run the wizard).
  • Network reachable (wifi or ethernet; Tailscale handles the rest once installed during Stage 1).
  • Disk space — at least 60 GB free for Xcode + DerivedData + simulator runtimes (for the xcodebuild role). ~10 GB is enough if the node only runs swift-test.
  • You do NOT need: Claude Code, agent skills, the studio repo cloned long-term (only during the bootstrap run — the wizard is self-contained), your iOS project's source, your editor setup.
Same username tip. Keep the same macOS short-username on the node as on the laptop when possible. Your project worktree lives at an absolute path that includes $HOME; same username on both sides means the path resolves identically, which is exactly what the dispatch layer assumes today.

Stage 1 — Network + SSH

Goal: ssh <node-hostname> true from the laptop succeeds without a password prompt.

On the node

1.1 · Install Tailscale manual

Download from tailscale.com/download/mac. Open the app, sign in with the same account you use on the laptop. Accept the "Add this machine" prompt in the admin console if shown.

Verify:

tailscale status        # should list this node + your laptop

Note the node's MagicDNS name (e.g. mini, or mini.tail-XXXXX.ts.net). You'll use it below.

1.2 · Enable SSH + Remote Login auto

The bootstrap wizard handles this as step 3. Manual equivalent:

sudo systemsetup -setremotelogin on

Or via UI: System Settings → General → Sharing → Remote Login: ON.

Security note. Remote Login accepts anyone with SSH credentials. With Tailscale in front, "anyone" narrows to devices on your tailnet. Still: use key-auth only, disable password-auth (below), and consider restricting the Remote Login to specific users in the Sharing pane.
On the laptop

1.3 · Copy the laptop pubkey to the node mixed

Easy path — requires one password entry:

ssh-copy-id <user>@<tailscale-hostname>
# e.g.
ssh-copy-id vishalsingh@mini

If that fails (missing ssh-copy-id, or you want manual control):

# Print the pubkey on the laptop:
cat ~/.ssh/id_ed25519.pub

# Then on the node, append it to authorized_keys:
mkdir -p ~/.ssh && chmod 700 ~/.ssh
cat >> ~/.ssh/authorized_keys <<'KEY'
ssh-ed25519 AAAAC3Nza... vishalsingh       # paste the line
KEY
chmod 600 ~/.ssh/authorized_keys

1.4 · Confirm BatchMode auth works auto

ssh -o BatchMode=yes <user>@<host> true && echo "OK"

If this prints OK without prompting, SSH is done.

First-connection TOFU. The very first ssh asks you to verify the host fingerprint. BatchMode=yes will fail on that prompt. Run one non-batch ssh <host> true first to accept the key into known_hosts; after that, batch mode works silently.

Stage 2 — Toolchain parity

Goal: the node can build + test the same code the laptop builds. That needs matching Xcode, simulators, and a handful of Unix tools.

On the node

2.1 · Xcode Command Line Tools manual

Minimum for the swift-test role:

xcode-select --install    # opens a GUI installer prompt

2.2 · Full Xcode.app manual

Required for the xcodebuild role. Install from the App Store, or download a specific version from Apple Developer Downloads if you need an older release.

After install, point xcode-select at it:

sudo xcode-select -s /Applications/Xcode.app
xcodebuild -version
Xcode version parity matters. Different Xcode = different SDK = different binaries. Builds dispatched to the node can diverge silently if the node is on an older Xcode. Run scripts/node-parity.sh any time you update Xcode on either machine — it surfaces toolchain drift across all registered nodes (#126).

2.3 · Homebrew + required packages auto

Bootstrap wizard handles this as step 6. Manual equivalent:

# Homebrew install (if missing)
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"

# Packages the studio scripts rely on
brew install jq rsync coreutils fswatch git

Why each:

  • jq — node registry parsing in dispatch scripts.
  • rsync — reference-image sync (and future source-sync work).
  • coreutils — gives you gtimeout for the SSH probe bounds.
  • fswatch — if the node will ever run Achilles workers locally.
  • git — Apple's shipped git is fine; brew's is fresher.

2.4 · Simulator runtimes manual

Open Xcode on the node, go to Settings → Platforms, and install the same iOS simulator runtimes your laptop has. xcrun simctl list runtimes on both machines — they should match. Any runtime missing on the node will make xcodebuild -destination lookups fail.

Stage 3 — Register with the studio

Goal: the laptop's dispatch scripts know about the node.

On the laptop

3.1 · Create or edit nodes.json mixed

mkdir -p ~/.dev-studio/.runtime

cat > ~/.dev-studio/.runtime/nodes.json <<'JSON'
{
  "schema": 1,
  "nodes": [
    {
      "id": "mini",
      "host": "mini",
      "user": "vishalsingh",
      "roles": ["swift-test", "xcodebuild", "snapshot-canonical"],
      "enabled": true
    }
  ]
}
JSON

Field reference:

FieldMeaning
idStudio-internal name; shows up in event payloads + lock-dir names. Use mini, studio, home-box etc.
hostWhat SSH / rsync connect to. Your Tailscale MagicDNS name.
usermacOS short-username on the node. Usually matches laptop's.
rolesWorkload tags the node can take. Drop roles the node isn't equipped for (e.g. no xcodebuild if you only installed CLT).
enabledSet false to pause the node without deleting its entry (maintenance / reboot).
Preference model — worth internalising. When multiple nodes advertise the same role, node-pick returns the least-loaded healthy one. When no remote advertises the role (or none are healthy), it returns local — that is, your laptop is always the implicit fallback, never a registered peer. "Keep the laptop free" is a real preference, not load-balancing.

Verify

Three quick checks from the laptop:

Reachability

scripts/node-health.sh mini
# expected: mini    healthy    0.42    mini

Role-based pick

scripts/node-pick.sh swift-test      # should print: mini
scripts/node-pick.sh xcodebuild      # should print: mini
scripts/node-pick.sh gpu             # should print: local (no node advertises this)

End-to-end dispatch

scripts/node-dispatch.sh mini echo "hello from $(hostname)"
# expected: hello from mini.local   (remote hostname, not the laptop's)

If all three pass: onboarding is complete. The next build that runs on a swift-test package or in full-green mode will land on the node.

Ongoing maintenance

Keep the node awake

macOS aggressively sleeps by default — including SSH sessions. On the node:

sudo pmset -a sleep 0          # never sleep the whole system
sudo pmset -a displaysleep 10  # screen can sleep — system stays up
sudo pmset -a disksleep 0      # don't spin disks down

Xcode / CLT parity drift

When you update Xcode on the laptop, the node falls behind and builds diverge silently. scripts/node-parity.sh probes every registered node and prints an aligned drift table — exit 1 means at least one dimension differs. Output is also cached at ~/.dev-studio/.runtime/node-parity-cache.json so dispatch-time guards (#136) read the verdict without re-probing.

scripts/node-parity.sh                # probe all nodes, print table
scripts/node-parity.sh m1mini         # probe just one
scripts/node-parity.sh --cache-only   # print last cached snapshot, no SSH

DerivedData cleanup

The node accumulates DerivedData per dispatched task. Monthly-ish:

ssh mini "du -sh ~/.dev-studio/.runtime/derived-data"
# If > 20 GB, clean:
ssh mini "rm -rf ~/.dev-studio/.runtime/derived-data/*"

Pause the node without de-registering

Edit ~/.dev-studio/.runtime/nodes.json on the laptop, flip "enabled": true to false. Dispatches fall back to local until you flip it back. Useful when the node is rebooting or you're mid-Xcode-update.

Always-on node (office Mac Studio)

A node you want permanently reachable — e.g. a Mac Studio in an office you occasionally visit — has a few extra settings beyond the home-mini case.

Auto-power-on after outage

sudo pmset -a autorestart 1    # boot automatically when AC returns

Auto-login

So the machine comes up fully operational after reboot, not stuck at the login screen. Carefully:

  • System Settings → Users & Groups → Login Options → Automatically log in as…
  • Filevault complicates this — if Filevault is on, first-boot-after-power-loss still requires password unless you've configured Filevault unlock credentials.
Physical access = full access. Auto-login + no Filevault means anyone at the machine can read everything. For an office context, weigh this against the operational benefit. At minimum: strong tailnet ACLs, full-disk encryption with institutional recovery, and no source credentials stored locally (signing certs / API keys are their own threat model — see Stage 3 onboarding).

Tailscale as a system service

macOS Tailscale app quits when the user logs out. For an always-on worker, install the CLI variant as a system service:

brew install tailscale
sudo tailscaled install-system-daemon
sudo tailscale up --ssh

This keeps the tailnet connection alive even without a logged-in GUI user.

Monitoring

For a node you can't walk over to, set up some ping of "is it alive":

  • Tailscale's admin console shows last-seen time — an alert on > 6-hour silence catches most failures.
  • A laptop-side cron that runs scripts/node-health.sh hourly and pings you (iMessage / Slack) on unreachable.

OS updates

Major macOS updates require user-at-the-keyboard confirmation. Plan a quarterly "visit the office node" window.

Security posture

A worker node accepts SSH from your laptop and runs build commands. That changes the machine's threat surface slightly — worth understanding what you're opting into and what mitigates it.

Two distinct threat axes

  • Network — who can reach the node over the wire.
  • Physical — who can sit at the keyboard or pull the disk.

They're orthogonal. A mini on your home network (shared wifi with a family member's laptop) has weak network isolation by default; a locked mini at an office has strong physical but potentially-weak network. Tailscale and FileVault each address one axis.

Network perimeter — Tailscale is the fence

With Tailscale in front, the node's SSH port is only reachable from devices signed into your tailnet. A family member on the same home wifi, not signed into your Tailscale account, cannot reach the mini's SSH — the port is invisible to them. That's the primary network mitigation. The alternative (raw SSH on the LAN IP) exposes the port to every device on the wifi; works, but weaker.

Tailscale ACLs can further restrict which tailnet devices can reach which — e.g. only the laptop can SSH the mini, other devices on your tailnet cannot. Default ACLs allow all-to-all within a personal tailnet; tighten via the admin console if you want defense in depth.

Physical posture — two recipes

ScenarioRecommended settings
Home mini (physically accessible family space)
  • FileVault ON — disk encrypted at rest.
  • Strong user password.
  • Auto-login OFF — someone at the keyboard sees the lock screen.
  • pmset -a sleep 0 so SSH stays reachable even while the console is locked.
  • Tailscale optional but recommended (shields from others on the wifi).
Trade-off: if the mini reboots (power outage), it sits at login until you type the password in. Acceptable for home because outages are rare.
Office studio (physically-controlled space, expected always-on)
  • FileVault ON.
  • Auto-login ON for a dedicated worker account (not your personal admin).
  • pmset -a autorestart 1 + pmset -a sleep 0 so a power blip → auto-reboot → auto-login → worker online within a minute.
  • sudo tailscaled install-system-daemon so Tailscale stays up regardless of GUI login state.
  • Keep signing keys / API tokens off this box unless they're in a service-account keychain you can rotate.
Trade-off: anyone with physical access to the office gets a logged-in session. Accept only if the office itself is trusted.

Multi-user isolation on the node

If other people have accounts on the same mini (e.g. shared home machine), macOS's per-user isolation protects most of your work — but some things leak across user boundaries even without admin privileges.

Visible to any logged-in userProtected (requires your password or admin)
Process list + command-line args (ps aux) — your project name + paths leak hereContents of files under your ~/
SSH-session presence (who, w, last)DerivedData + build outputs
CPU / memory / network activity (Activity Monitor)Your keychain (signing certs, etc.)
Aggregate disk usage (df)SSH authorized_keys, known_hosts
Outbound network connections (lsof -i)Shell history, browser state
Admin = game over. Any user with sudo can read everything on the disk. Only grant admin to accounts whose work you'd be comfortable reading in return. For a shared home mini: you're admin, everyone else is a Standard user.

What the SSH layer itself does + doesn't change

  • Enabling Remote Login does not grant new physical access. Someone at the keyboard still needs your password to unlock the console; they can't use your SSH session from the desk.
  • SSH runs as a system daemon — you don't need to be logged in at the console for the laptop to dispatch jobs. The daemon accepts authenticated key-auth connections independent of GUI login state.
  • BatchMode=yes + key-only auth (what the bootstrap wizard configures) means passwords aren't in the picture for remote access at all — only holders of your private key (you) can reach SSH, even from inside the tailnet.

Troubleshooting

ssh <host> true hangs then fails
Host isn't reachable on the tailnet. tailscale status on both machines — both should list each other. If not, re-login on whichever shows offline. If Tailscale is fine but SSH still hangs: Remote Login isn't enabled on the node. Stage 1.2.
Permission denied (publickey) on SSH
Pubkey not installed, or installed for the wrong user. On the node: cat ~/.ssh/authorized_keys should contain the exact line from the laptop's ~/.ssh/id_ed25519.pub. Permissions matter: ~/.ssh must be 700, authorized_keys must be 600.
Host key verification failed
First-connect TOFU wasn't done. Run ssh <host> true without BatchMode, accept the fingerprint prompt, then retry. If the node was reinstalled, its host key changed — remove the stale entry: ssh-keygen -R <host>.
node-pick.sh <role> prints local when you expected the node
Run scripts/node-health.sh with no args. Look for the node's row:
  • unreachable → SSH / Tailscale problem (above).
  • disabled → nodes.json has "enabled": false.
  • unknown → wrong id in your command (spelling).
  • Healthy but node-pick still says local → role missing from the node's roles array.
Dispatch works for echo but xcodebuild on the remote fails
Usual culprits: (1) project source not present on the node at the same path — that's the source-sync gap, unsolved pre-Phase-2.5-H + pending auto-rsync work; (2) Xcode version mismatch; (3) missing simulator runtime. Compare xcodebuild -version and xcrun simctl list runtimes on both sides.
MagicDNS name doesn't resolve
On the laptop: System Settings → Network → your connection → DNS → Search Domains should include your tailnet name (e.g. tail-XXXXX.ts.net). Tailscale adds this automatically but some VPN or corporate-network configs strip it. Workaround: use the full FQDN (mini.tail-XXXXX.ts.net) in nodes.json.
Builds are slower on the node than on the laptop
Expected on the first build — DerivedData is cold. Subsequent builds should match or exceed the laptop depending on silicon. If consistently slow: (1) check node-health's load-avg — another process may be hogging CPU; (2) verify the node has enough RAM (8 GB is tight for modern Xcode); (3) check disk is SSD, not spinning.
SSH works but rsync fails
rsync defaults don't carry over BatchMode. Test with rsync -av -e "ssh -o BatchMode=yes" /tmp/test.txt <host>:/tmp/. If that fails, either rsync isn't installed on the node (brew install rsync) or the remote shell profile is printing something to stdout (check ~/.zshrc / ~/.bash_profile for echoes on non-interactive sessions — strip them).
