# Router Pattern

Convention for skills that have grown multiple distinct modes. Replaces the "one big SKILL.md loads everything" default. Goal: cheap invocations, fluid in-session mode switches, predictable cold-start cost.

## When to router-ize

Apply the pattern when a skill meets **any** of:
- Three or more distinct sub-commands with non-overlapping prose.
- SKILL.md exceeds ~500 lines.
- Cold-start latency is user-visible.
- Different modes need different state snapshots.

Do **not** router-ize single-purpose skills (Argus today). The overhead of a router file and mode-pack split is only justified when it saves real load cost.

## Three parts

### 1. Router (always loaded)

The `<skill>/SKILL.md` file *is* the router. Must stay small — rule of thumb **<100 lines** total prose excluding frontmatter.

Responsibilities:
- Frontmatter (name, description, type).
- One-paragraph statement of what the skill is.
- A dispatch table: `<sub-command> → modes/<pack>.md`. One line per mode.
- Intent detection rules: command arg first (explicit), natural-language intent second (fallback), single default mode if ambiguous.
- Pointer to `singleton-invariants.md` if the skill is singleton.
- Pointer to this file for the pattern contract.

The router does **not** contain mode-specific prose, workflows, or state manipulation. If you find yourself writing "for mode X, do Y" in the router, that prose belongs in the mode pack.

### 2. Mode packs (loaded on demand)

`<skill>/modes/<pack>.md` — one file per mode. Self-contained: prose + step-by-step + error-handling + post-conditions.

Responsibilities:
- Declares which snapshots it needs (up front, in frontmatter or an opening block).
- Full workflow for that mode.
- Emits events per `_shared/contracts/events.md`.
- Calls into other mode packs via filesystem artifacts (snapshots, briefs, design docs), **not** direct imports — mode packs don't load each other.

Mode-pack size: no hard limit, but if one mode pack exceeds ~400 lines consider splitting further.

### 3. Snapshots (loaded by mode pack, per domain)

`<skill>/snapshots/<domain>.md` or `<skill>/snapshots/<domain>.json` — small per-domain state files. One domain = one file.

Examples for Chanakya: `briefs.json`, `debt.json`, `feedback-inbox.json`, `events-tail.json`.

Each snapshot:
- Has a `generated_at` timestamp and a `schema` version integer in its payload.
- Is regenerated by a known producer (usually the mode that *writes* the underlying state, or a dedicated `snap` mode).
- Is *read* by any mode that needs it.
- Is at most one page of content — if a snapshot would be huge, it's the wrong shape (summarize aggressively, link to the raw source for detail).

Modes load **only the snapshots they need**, never the full set.

## Freshness and fallback

The router and every mode pack must treat snapshots as hints, not truth. Contract:

1. Read the snapshot.
2. Compare `generated_at` against a mode-specific staleness window (e.g. status mode tolerates 1h stale briefs snapshot; brief mode requires <5min).
3. If stale, the mode pack is responsible for refreshing or falling back to reading the underlying source directly.
4. Never silently operate on stale snapshots — log the decision in an event.

Corollary: deleting any snapshot is always safe. Modes always have a full-load fallback path. Snapshots are an optimization, not a dependency.

## Intent detection

Priority order the router walks when dispatching:

1. **Explicit arg** — `/chanakya brief` → `modes/brief.md`. Always wins.
2. **Conversational switch** — mid-session, if the user says "let's plan instead" and the currently-loaded mode is different, the router re-dispatches inline without requiring a new invocation. This is the main UX upgrade over the pre-router design.
3. **Default** — if no arg and no clear intent, dispatch to the skill's default mode (e.g. Chanakya → `status`).

Router must never prompt the user for clarification when a sensible default exists. Asking is a regression vs the pre-refactor behavior.

## Forward-compat

Adding a new mode = add one file to `modes/` + one dispatch line to the router. No shared state in the router beyond dispatch. This keeps growth cheap.

Removing or renaming a mode is a breaking change (user-invocable surface) — follow REVIEW.md ask-tier procedure.

## What this supersedes

- The "cold-start optimization" conversations prior to this refactor (issue #33 levers A/B/C).
- Any "conditional Step 0 skip" logic — modes now load only what they need, so there is no universal Step 0 to skip.
- Any "snapshot file + thin reader" proposals — snapshots are a first-class part of the pattern, not a separate fast path.

## Applied to

- **Chanakya:** full refactor (Phase 2 of intent-router work).
- **Achilles:** full refactor (Phase 3).
- **Lu Ban:** router-first from birth (Phase 4).
- **Argus:** not applied today; revisit if SKILL.md crosses 500 lines.

## Invariants not negotiable

- Router file always small (<100 lines prose).
- Mode packs never cross-load other mode packs.
- Snapshots always have a fallback path.
- Every existing sub-command and flag is preserved through a router refactor — no renames, no removals without ask-tier review.
- Singleton skills stay singleton — see `_shared/patterns/singleton-invariants.md`.
