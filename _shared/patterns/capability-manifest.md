# Capability Manifest Pattern

The studio has ~30 mode packs across Chanakya, Achilles, Argus, and upcoming Lu Ban + Chiron folds. Tracking capabilities by hand across that surface is drift-prone. The capability manifest is a machine-readable roster, regenerated from mode-pack frontmatter on every commit — like `docs-surface.json`, but deeper.

## Shape

`_shared/schemas/capability-manifest.json`:

```json
{
  "schema_version": {
    "name": "capability-manifest",
    "version": "1.0.0",
    "min_reader": "1.0.0",
    "deprecated_at": null
  },
  "generated_at": "2026-04-22T14:32:01Z",
  "agents": [
    {
      "name": "achilles",
      "router": "achilles/SKILL.md",
      "modes": [
        {
          "name": "task",
          "path": "achilles/modes/task.md",
          "type": "mode-pack",
          "reads": ["~/.dev-studio/<project>/plans/chanakya-tasks/*.md", "…"],
          "writes": ["~/.dev-studio/<project>/plans/debriefs/<debrief-id>.yaml", "…"],
          "snapshots": [],
          "dry_run": true,
          "budget_tokens": 6000
        }
      ]
    }
  ]
}
```

## Rules

1. **Committed, not runtime-only.** Per Q7, the manifest lives in the repo tree and is regenerated by the pre-commit hook. Stale manifests trigger `W_CAPABILITY_STALE` (warn permanent — user regenerates intentionally during analysis sessions).
2. **Self-versioned.** `schema_version.name = "capability-manifest"`, starts at `1.0.0`. Bumps follow `schema-version.md` rules.
3. **Router-level `reads` / `writes` are the union of its modes.** Never hand-maintained. The generator script computes the union.
4. **Dry-run flag.** Each mode declares `dry_run: true | false` in its frontmatter. The manifest surfaces the flag so orchestrators can filter.
5. **Validator asserts consistency.** Pre-commit runs `scripts/capability-manifest.sh --validate` which checks:
   - Every `modes/*.md` has an entry.
   - Every entry's `reads` / `writes` match the source frontmatter.
   - No stale entries for deleted modes.
   - `schema_version` is current.
6. **CHANGELOG — `_shared/schemas/capability-manifest-CHANGELOG.md`.** Human-readable entries when capabilities change (new mode, removed mode, breaking frontmatter change).

## Generator — `scripts/capability-manifest.sh`

```
usage: scripts/capability-manifest.sh [--regen | --validate]
```

- `--regen` — read every `*/SKILL.md` and `*/modes/*.md`, emit the manifest, write atomically to `_shared/schemas/capability-manifest.json`.
- `--validate` — diff the generated manifest against the committed one; exit 1 if they differ. Used by pre-commit.
- No args — prints the manifest to stdout.

## Pre-commit wiring

The pre-commit hook chains:

```
update-surface-manifest.sh   # existing
capability-manifest.sh --regen   # new in Commit E
capability-manifest.sh --validate   # new in Commit E (auto-stages the regenerated file on drift)
lint-architecture.sh --staged
```

`--regen` always runs; `--validate` is a belt-and-suspenders check that the regen produced the same content as the committed file. If they differ, the hook auto-stages the regenerated file (matching the `docs-surface.json` pattern).

## What this replaces

- Ad-hoc grep-through-mode-pack-frontmatter when an orchestrator needs to know what exists.
- Mental roster of "which modes support dry-run" / "which modes read the event log".
- Drift between `chanakya/SKILL.md` dispatch table and the actual `modes/` directory.

## Non-goals

- Runtime capability negotiation. The manifest is static at commit time; orchestrators read it directly, no handshake.
- Per-version capability diffs. CHANGELOG covers human-readable changes.
- Cross-repo aggregation. One manifest per studio instance.
